# Phase 2 问答回答策略

8 类常见问题的回答指引。核心原则：**以用户理解为中心**——根据问题类型调整回答的深度、结构和侧重点。

---

## 1. 概念解释

**识别**：用户遇到不熟悉的术语/缩写/方法名/数学概念，问"X 是什么"、"介绍一下 X"

**目标**：用户看完能**独立向别人解释 X**，不需要引用论文原文

**策略**（逐层展开，每项都覆盖）：

1. **一句话定义** — X 是做什么的/解决什么问题的
2. **在论文中的位置** — X 在这篇论文的哪个模块/公式/阶段出现，承担什么角色。引用 Section X, Eq X, Figure X
3. **工作原理** — X 怎么工作的，用简单的逻辑链讲清楚。不堆公式/代码，除非公式本身是答案。可以用类比帮助理解
4. **关键设计细节** — X 区别于同类方法的关键设计点（1-3 个），每个讲清楚"为什么这么设计"。失败的设计也要提及
5. **与其他概念的关系** — X 和论文中其他概念的关联和区别。如果用户本次会话中已经问过或讨论过相关概念，**必须显式建立连接**："你之前问的 Y 和 X 的关系是..."
6. **（可选）补充素材** — 如果理解 X 需要前置知识，先铺垫。如果有拓展阅读价值的概念，用 `[[概念]]` 标注

**反模式**：
- 只给一句话定义就停了
- 直接复制论文原文而不做解释
- 假设用户了解相关背景术语

---

## 2. 方法细节

**识别**：追问模块/算法的具体实现，"怎么做到的"、"具体怎么实现的"

**策略**：
1. **直接回答核心问题** — 是/否/怎么做，不绕弯
2. **引用论文原文** — 具体段落/公式/图表编号作为证据
3. **如果论文没有明确说明** — 诚实指出，给出合理推断并标注"这是我的推断"
4. **区分来源** — "论文说了 X" vs "我推断 Y" vs "根据领域常识 Z"

**示例**："MTP 是级联的吗，如果是级联，如何并行呢" → 先回答"是，级联的" → 解释为什么能并行 → 区分论文明说的和推断的

---

## 3. 问题定位

**识别**：用户搞不清楚这篇论文的定位——"到底解决什么问题"、"输入输出是什么"、"主要做什么任务"。如果用户**反复问同类问题**，说明之前的解释太复杂，需要降维到更简单的类比

**目标**：用户看完后能用**自己的一句话**向别人解释这篇论文做什么

**策略**（按顺序）：
1. **一句话定义** — "这篇论文做了一件什么事"
2. **目标** — 要解决什么痛点/达到什么目的
3. **输入输出** — 给什么、返回什么，用最简单具体的示例
4. **为什么需要它** — 之前怎么做、之前的问题、这个方法带来了什么改变
5. **核心思想** — 1-2 个最关键设计，不展开细节
6. **应用场景** — 在哪里用，为什么适合
7. **开放入口** — 结束时提示"要不要深入某个具体模块"——让用户主导深度

---

## 4. 设计动机

**识别**："为什么这样设计"、"为什么不选 X 方法"、"设计选择背后的考虑"

**策略**：
1. **论文中的理由** — 引用原文论据或实验证据
2. **领域常识补充** — 这个方法在该领域的常见权衡
3. **失败的尝试** — 论文中试过但放弃的方案（如有），往往比成功的选择更有信息量
4. **区分视角** — "作者这么做的原因" vs "客观上为什么这是好的选择"

---

## 5. 实验分析

**识别**：关注实验设计、结果解读、数据细节

**策略**：
1. **先数字，再解读** — 给出具体数值，然后解释含义
2. **关联到方法** — 实验结果是某个设计选择的直接证据
3. **反直觉结果** — 如果某个结果看起来反常，明确指出并讨论可能原因
4. **区分来源** — "论文中的结论" vs "我独立观察到的"

---

## 6. 对比分析

**识别**：理解这篇论文和其他工作的关系，"和 X 比有什么本质区别"、"能结合吗"

**策略**：
1. **列表差异** — 用表格快速呈现关键差异
2. **讲每个差异的含义** — 不只是"不同"，而是"为什么不同"和"带来什么后果"
3. **跨论文建立连接** — 如果用户之前读过相关论文，引用那篇笔记的具体内容
4. **区分来源** — "论文自己做的对比" vs "我帮你做的对比"

---

## 7. 局限与批判

**识别**：挑战论文前提、方法或结论，"这个能在真实场景用吗"、"有什么问题"

**策略**：
1. **先引用论文自述的 limitation** — 论文承认的问题
2. **补充观察到的潜在问题** — 论文没提但你注意到的
3. **具体理由** — 每个质疑要有具体依据，不做无根据的批评
4. **区分严重性** — "可以通过后处理修复的" vs "方法论层面的根本问题"

---

## 8. 扩展思考

**识别**：用户想把这个方法用到自己的场景，"能用到 X 吗"、"如果换一个 backbone 会怎样"

**策略**：
1. **分析可行性** — 输入输出接口是否兼容、核心假设是否成立
2. **指出适配的主要挑战** — 不是"应该不行"，而是"如果要行，需要解决 X"
3. **引用相关工作** — 如果有人尝试过类似扩展，引用
4. **鼓励实验验证** — 不做纸上推演的最终判决
